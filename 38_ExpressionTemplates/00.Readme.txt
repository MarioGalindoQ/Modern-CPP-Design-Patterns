# EXPRESSION TEMPLATES / LOOP FUSION (PERFORMANCE)
**Author:** Mario Galindo Queralt, Ph.D.

## Intent
To represent mathematical expressions as a tree of objects at compile-time, deferring the actual
computation until the result is assigned to a container. This technique enables the compiler to
perform **Loop Fusion**, executing complex multi-operator expressions in a single, continuous
pass over the data without allocating intermediate temporary objects. This is the architectural
foundation for world-class linear algebra libraries such as **Eigen** and **Blaze**.

## The Problem: Naive Overloading and the "Memory Wall"
In traditional C++ development, mathematical operator overloading (e.g., `R = 2*(A + 3*B + 4*C)`)
is intuitive for the programmer but disastrous for hardware efficiency when dealing with massive
datasets:

1. **Intermediate Temporaries (Heap Pressure):** Every sub-expression (like `3*B` or `A + 3*B`)
creates a full-sized temporary `Vector` on the heap. With 1.2 billion elements (~8.94 GB per
vector), a single expression can easily trigger **OS Swapping** or 'std::bad_alloc', as the memory
footprint peaks far beyond physical RAM capacity.
2. **Multiple Cache Passes:** The CPU is forced to traverse the memory several times—once for
each operator. This results in redundant data transfers between the RAM and the CPU Cache,
hitting the "Memory Wall" where the CPU remains idle waiting for data.
3. **ALU Throughput Limitation:** Traditional overloading prevents the compiler from optimizing
the instruction pipeline across operator boundaries. Each operator is a self-contained function
call that returns a finished object, preventing the Arithmetic Logic Unit (ALU) from working at
its theoretical maximum speed.

## The Solution: Lazy Evaluation and Static AST with Loop Fusion
Expression Templates solve these issues by changing the fundamental nature of mathematical
operators. Instead of returning a result, they return a lightweight **Proxy Object** (a node in a
compile-time Abstract Syntax Tree).

- **Lazy Evaluation:** No calculation is performed when the expression is defined. The proxies
    only store references to the operands and the logic of the operation.

- **Loop Fusion:** The actual computation is "pushed" into the assignment operator (`operator=`)
    of the target vector. The entire expression tree is collapsed into a single 'for' loop,
    ensuring that each data element is loaded into the CPU cache only once.

- **Inlining & Machine Code Parity:** Since the AST is resolved at compile-time, the compiler can
    apply aggressive **Inlining**. The generated machine code for `R = A + 2*B + 3*C` becomes
    identical to a hand-written loop: `R[i] = A[i] + (2.0*B[i]) + (3.0*C[i])`.

## Our Examples
This directory illustrates the evolution of this technique, from the baseline problem to the
state-of-the-art C++23 solution:

1. **01_Traditional/:**
   A professional baseline implementation using **Move Semantics** to recycle buffers. It serves
   as the benchmark to measure the physical limitations of sequential execution.
2. **02_Expressions_CRTP/:**
   The classic implementation using the **Curiously Recurring Template Pattern (CRTP)**. It
   demonstrates how to build a static AST where the base class is a template that "knows" its
   derived type.
3. **03_Expressions_Deducing_This/:**
   The modern C++23 evolution using C++23 "Deducing This". It uses **Explicit Object Parameters**
   to achieve the same performance as CRTP but with significantly cleaner syntax and better
   maintainability.

## OO Principles Applied (from 002_OO_Principles.txt)
- **SRP (Single Responsibility):** Each expression node (`VecSum`, `VecScale`) is dedicated
    solely to representing a specific mathematical operation as a data structure.
- **OCP (Open/Closed):** The system is perfectly open for extension; adding a new operation
    (e.g., `VecDot` or `VecSub`) only requires a new node class, without modifying the core
    `Vector` container.
- **DIP (Dependency Inversion):** The `Vector` class depends on the `VecExpression` abstraction,
    not on concrete operation types, making it agnostic to the complexity of the tree it is
    evaluating.
- **CQS (Command-Query Separation):** Expression nodes are pure "Queries" (they provide data via
    `operator[]` without side effects), while the `Vector` assignment is a "Command" that
    executes the final mutation.

## Cross-References to Other Patterns
- **Pattern 14 (Proxy):** Every node in the expression tree is a functional Proxy representing a
    pending calculation.
- **Pattern 10 (Composite):** The expression tree is a static version of the Composite pattern,
  where nodes can be combined into complex hierarchical structures.
- **Pattern 20 (Interpreter):** This is the high-performance evolution of the Interpreter
    pattern, where the "grammar" is resolved by the compiler rather than a runtime engine.
- **Pattern 32 (CRTP):** The underlying engine for the static polymorphism used in Example 02.
- **Pattern 33 (Deducing This):** The modern C++23 language feature that simplifies the
    implementation in Example 03.
