# DECORATOR PATTERN (STRUCTURAL)
**Author:** Mario Galindo Queralt, Ph.D.

## Intent
The Decorator pattern is a structural design pattern that allows you to 
attach additional responsibilities to an object dynamically or statically. 
Decorators provide a flexible alternative to sub-classing for extending 
functionality without modifying the original class.

## The Problem
Inheritance leads to a rigid class explosion. If you want to add multiple 
independent features (e.g., Milk, Sugar, Encryption, Logging, Alarms) to 
different base classes, creating a subclass for every possible combination 
becomes unmanageable.

## The Solution
Instead of creating dozens of subclasses, the Decorator pattern "wraps" 
the core object. In C++, this is achieved through two main paradigms:

1. **Dynamic (Runtime):** The Decorator wraps a component using composition 
   (pointers). This allows adding or removing features while the program 
   is running (e.g., building a custom coffee).
2. **Static (Compile-time):** The Decorator wraps a component using 
   templates and Mixin Inheritance. The structure is fixed at compilation 
   for maximum performance, but modern C++ allows these structures to be 
   highly configurable.

## Our Examples
This folder illustrates the evolution of the Decorator pattern:

1. **01_Simple/:**
A basic dynamic implementation using 'std::unique_ptr'. It shows the 
fundamental wrapper mechanism and how costs and descriptions are 
accumulated through a recursive chain of calls.

2. **02_Advanced/:**
A sophisticated dynamic version where decorators have internal state 
(portions, types) and complex string logic to build natural sentences.

3. **03_Static_Mixin/:**
Demonstrates "Static Decorators" using template inheritance. It models a 
"Coffee Machine Factory" where recipes are pre-defined. It offers zero 
runtime overhead but suffers from "Interface Loss" when calling methods 
defined in the base class.

4. **04_Static_Deducing_this/ (Modern C++23):**
The most advanced version. It models an **Industrial Sensor system** and 
leverages C++23 **"Deducing This"** to solve the "Interface Loss" problem. 
By using 'this auto&& self', every layer of the decorator chain remains 
visible, allowing for a perfectly-typed Fluent Interface and **Runtime 
Calibration** of static structures.

## Key Benefits
- **Single Responsibility Principle:** Each decorator handles one feature.
- **Open/Closed Principle:** Add new decorators without modifying existing 
  code.
- **Performance (Static):** Compile-time decorators allow for aggressive 
  inlining and zero memory indirection.
- **Interface Persistence (C++23):** Modern static decorators preserve the 
  identity of the outermost wrapper, ensuring the full API is always 
  available regardless of the calling depth.
