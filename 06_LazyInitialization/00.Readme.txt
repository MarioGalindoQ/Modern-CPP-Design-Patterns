# LAZY INITIALIZATION PATTERN (CREATIONAL)
**Author:** Mario Galindo Queralt, Ph.D.

## Intent
Lazy Initialization is an optimization technique that delays the creation 
of an object, the calculation of a value, or any other expensive process 
until the first time it is actually needed. It is a form of lazy evaluation.

## The Problem
Initializing resources prematurely consumes memory, CPU cycles, and slows down 
application startup times, especially when dealing with objects that might 
never be used during the program's lifecycle.

## The Solution
The core principle involves using a conditional check (often within an 
accessor method) to determine if the resource has already been created:
1. Check: When the object is requested, verify if an instance exists.
2. Initialize: If it does not exist, create it at that exact moment.
3. Cache/Return: Store the instance and return it to the caller for this 
and all subsequent requests.

## Our Examples
This folder illustrates two distinct architectural levels of Lazy Initialization:

1. **01_Lazy_Traditional/:**
Demonstrates "Factory-Level" Lazy Initialization. It uses a 'Fruit' factory 
that acts as a Flyweight/Lazy cache, managing a collection of shared 
instances via 'std::map' and 'std::shared_ptr'.

2. **02_Lazy_Deducing_this/ (Modern C++23):**
Demonstrates "Object-Level" Lazy Initialization. It uses a **Transparent 
Infrastructure Mixin** and C++23 **"Deducing This"**. This allows heavy 
objects to exist as lightweight shells that automatically trigger their 
internal resource loading upon the first functional call, without using 
virtual functions or the CRTP idiom.

## The C++23 Advantage (Technical Evolution)
Traditional object-level lazy loading usually requires:
- **Manual Checks:** Repeating the 'if(!initialized)' logic in every method.
- **Virtual Functions:** Incurs the cost of a VTable and dynamic dispatch.
- **CRTP:** Incurs complex circular template syntax.

With **"Deducing This" (Explicit Object Parameters)**, we achieve **Static 
Dispatch Polymorphism**. A non-template base class (the Mixin) can "reach 
down" into the derived class at compile-time to trigger initialization. 
This provides the performance of static code with the elegance of a reusable 
infrastructure layer, keeping the business logic clean and transparent.

## Key Benefits
- **Improved Startup:** Avoids heavy initialization at program launch.
- **Memory Efficiency:** Defers resource allocation, keeping the footprint low.
- **Transparency:** Modern implementations allow lazy loading to be invisible 
  to the end-user (The "Transparent Lazy Load" idiom).

### Relationship with Singleton & Registry
- **05_Singleton**: Lazy Initialization is the core mechanism used by most 
modern Singletons (like Meyers' Singleton) to ensure the object is only 
created when first accessed.
- **16_Register**: While a classic Singleton restricts a class to one 
instance, our implementation of Lazy Initialization acts as a **Multiton** 
(a simplified version of the Registry pattern).
