# BUILDER PATTERN (CREATIONAL)
**Author:** Mario Galindo Queralt, Ph.D.

## Intent
To separate the construction of a complex object from its representation, 
so that the same construction process can create different representations.

## The Problem
Constructing a complex object step-by-step often requires a client to invoke 
multiple methods. If a client object directly creates an instance of a 
builder and invokes the required methods, it must be fully aware of the 
construction logic. Consequently, whenever the construction logic undergoes 
a change, all client objects need to be modified accordingly. This approach 
creates tight coupling and violates the open/closed principle.

## The Solution
The Builder pattern introduces a level of separation to address this problem:
1. **Builders:** The different steps in the construction process are declared 
as methods of a common interface, to be implemented by different concrete 
builders.
2. **The Director:** Instead of having clients invoke builder methods directly, 
a dedicated object called a "Director" is used. The Director is responsible 
for executing the builder methods in the correct sequence to construct 
the final object.

Different clients can use the Director object to create the required product. 
Once the construction process is finished, the client can directly request 
the fully constructed object from the builder (often facilitated by a 
'getObject' or 'build' method declared in the Builder interface).

## Our Examples
This folder illustrates three distinct architectural approaches to the Builder:

1. **01_Static_example/:**
Shows a "Flat Fluent Builder" that manages a complicated constructor on the 
stack. It uses 'return *this' for method chaining and an implicit conversion 
operator for a seamless building process.

2. **02_Dynamic_example/:**
A heap-based approach returning a 'std::unique_ptr<Car>'. Ideal for complex 
objects with polymorphic components or life cycles that exceed the local scope.

3. **03_Static_Deducing_example/ (Modern C++23):**
The most advanced version. It demonstrates how to implement a **Hierarchical 
Builder** using the C++23 feature **"Deducing This"** (Explicit Object 
Parameters). It solves the problem of "losing the derived type" in 
inheritance chains without the complexity of the CRTP idiom.

## Memory & Performance Trade-offs (Engineering Note)
While all examples share a "Fluent" interface, they serve different needs:

- **Static/Stack Versions (01 and 03):**
  - **Performance:** Maximum speed due to cache locality and zero heap overhead.
  - **Deducing This Advantage (03):** Allows the builder to be split into 
      multiple specialized classes (e.g., PhysicalProps -> CarBuilder). 
      Methods in the base class automatically return the derived type 
      using 'this auto&& self', enabling hierarchical fluent interfaces.
  - **Memory:** Uses 'std::variant' and 'std::array' for Stack Polymorphism.
  - **Constraint:** Strictly limited by the System Stack size. Best for
      high-frequency, local operations with a predictable number of objects.
  - **Semantics:** Typically supports Value Semantics (Copy/Move) as long as its
      components allow it.

- **Dynamic/Heap Version (02):**
  - **Scalability:** Limited only by available RAM; prevents Stack Overflow 
      for very large objects.
  - **Flexibility:** Uses 'std::unique_ptr' for traditional Dynamic 
      Polymorphism.
  - **Cost:** Higher latency due to heap allocation and pointer indirection.
  - **Semantics:** Often Move-Only (Identity Semantics), ensuring that complex
      resources are never accidentally cloned.

**MGQ NOTE:** All implementations follow the **"Rule of Seven"** for lifecycle 
management, ensuring that regardless of whether the object lives on the Stack 
or Heap, its construction, transfer, and destruction are explicitly controlled 
and exception-safe ('noexcept').

## Key Benefits
- **Encapsulation:** Clients do not deal with construction steps.
- **Modularity:** Adding a new builder implementation is easy and non-intrusive.
- **Finer Control:** Construction process is independent of the actual 
components, providing total control over assembly.
